# Execution Protocol

## 1. Одно активное TODO

В любой момент времени допускается только **одно** задание со статусом `ACTIVE`.

Статусы:
- `QUEUED`
- `ACTIVE`
- `BLOCKED`
- `DONE`

Нельзя параллельно развивать несколько архитектурных веток, если это разрушает возможность безопасного handoff.

## 2. Единица работы

Единица работы — отдельный файл `tasks/TASK-XXX-*.md`.

Каждое задание обязано содержать:
- цель;
- входы и зависимости;
- ожидаемые артефакты;
- подробные шаги;
- уровень проверки;
- критерий завершения;
- handoff-пакет;
- safe pause point.

## 3. Рабочий цикл

1. Назначить одно задание `ACTIVE`.
2. Прочитать зависимости и связанные файлы.
3. Выполнить только шаги этого задания.
4. Зафиксировать решения в документации или коде.
5. Пройти нужный verification level.
6. Обновить handoff-пакет.
7. Перевести задачу в `DONE` или `BLOCKED`.
8. Только после этого активировать следующую задачу.

## 4. Safe pause rules

Можно безопасно остановиться только если:
- изменённые файлы сохранены;
- текущее промежуточное состояние описано;
- есть понятный next step;
- диагностика или документация уже отражают новое состояние.

Нельзя останавливаться в точках, где:
- формат данных изменён, но миграция не описана;
- launcher уже пишет новый state, а чтение ещё старое;
- plugin tools уже регистрируются, но effective mode ещё не ограничен;
- плагин уже подключён к области или глобально, но не зафиксировано, как это хранится и как восстанавливается.

## 5. Handoff discipline

Каждая остановка обязана оставить после себя:
- что сделано;
- какие файлы изменены;
- какие решения зафиксированы;
- какой verification level достигнут;
- что осталось открытым;
- какая следующая задача должна стать `ACTIVE`.

Используй `HANDOFF_TEMPLATE.md`.

## 6. Checkpoint не равен completion

Промежуточные формулировки вроде:
- `checkpoint`
- `baseline`
- `foundation completed`
- `resume later`

не означают завершение инициативы.

Если работа остановлена до закрытия всех задач, исполнитель обязан явно написать:
- какие task ids уже `DONE`;
- какие task ids ещё `ACTIVE`/`BLOCKED`/`QUEUED`;
- почему инициатива ещё не завершена;
- что именно требуется до `TASK-014`.

## 7. Scope reduction запрещён без отдельного разрешения

Исполнитель не имеет права самостоятельно:
- сузить инициативу до milestone;
- остановиться на baseline plugin;
- считать foundation достаточным финалом;
- объявить partial implementation завершением всей программы работ.

Если реализация временно остановлена на checkpoint, это должно быть оформлено как незавершённый промежуточный результат, а не как финал.

## 8. Правило завершения инициативы

Инициатива считается завершённой только если одновременно:
- `TASK-001` ... `TASK-014` имеют статус `DONE`;
- нет открытых blocker-ов;
- пройден обязательный verification path до `V4`;
- выполнен `MASTER_COMPLETION_CHECKLIST.md`.

## 9. Непересматриваемые инварианты инициативы

На протяжении всех задач должны сохраняться следующие правила:
- сохранённая рабочая область строится **на основе** существующего `PATH[N]`, а не отрывается от него;
- выбор пути фактически выбирает workspace, access mode и environment config;
- у области окружение считается `DEFAULT`, пока к ней не подключён хотя бы один плагин и для него не сохранены area-specific настройки;
- plugin tools регистрируются через универсальный registry contract;
- подключение плагина должно учитывать пользовательский выбор: в текущую конфигурацию области или глобально;
- контракт должен быть пригоден и для БД, и для внешних AI/subagent-плагинов;
- итоговая документация должна позволять генерировать совместимые плагины внешней нейросетью.
