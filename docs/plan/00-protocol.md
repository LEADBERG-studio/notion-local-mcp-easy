# Tunnellio WSS: контракт протокола

**Статус:** черновик к утверждению
**Дата:** 2026-08-08

Этот файл замораживается ПЕРВЫМ. Пока он не утверждён, ни сервер, ни клиент писать нельзя: две стороны разъедутся, и стыковка съест больше времени, чем сама разработка.

Рядом лежат: `01-relay.md` (сервер), `02-client.md` (Go-клиент), `03-mcp-contour.md` (контур в Notion Local MCP Easy).

---

## 1. Зачем

Сейчас туннели строятся через `ssh -R`. Это работает, но:

* **Антивирус ругается всегда.** Детект поведенческий: `ssh -R` это готовое правило у Elastic, Sigma, Fortinet, CrowdStrike и Defender (MITRE T1572, Command and Control). Подписанный Microsoft `ssh.exe` ловят точно так же, потому что флагают не файл, а паттерн запуска. Отсюда важный вывод: покупка сертификата эту проблему не решает.
* **Порт 22 закрыт** во многих корпоративных сетях.
* **Зависимость от чужого relay.** У Serveo были проблемы с сертификатом, и не работало вообще ничего.

Исходящее TLS на 443 неотличимо от браузера. Так работают ngrok и cloudflared, поэтому на них и не ругаются.

## 2. Границы

**В объёме:** исходящий WSS на 443, мультиплексирование, маршрутизация по Host, случайные и зарезервированные поддомены, API-ключи, квоты.

**Вне объёма пока:** TCP для произвольных портов, UDP, контроль доступа на relay (IP allow-list, basic-auth перед туннелем), веб-консоль. Это следующий этап, но протокол не должен закрывать к нему дорогу.

## 3. Транспорт

```
Клиент                      Caddy (443)                Relay (localhost)
  |                              |                          |
  |--- TLS + WSS /connect ------>|--- HTTP upgrade -------->|
  |<========= одно WS-соединение, внутри yamux =============|
```

* **Только WSS на 443.** Порт 80 существует лишь для редиректа.
* **Мультиплексирование: yamux поверх WebSocket.** Свой фрейминг не изобретаем: keep-alive, backpressure и полузакрытые потоки там уже отлажены. Реализации есть в Go (`hashicorp/yamux`), Python и Rust.
* **Один туннель = одно WS-соединение = один yamux-сеанс.** Каждый входящий HTTP-запрос это отдельный поток.
* Кадры WebSocket **бинарные**, текстовые не используются.

## 4. Установление сеанса

Клиент открывает `wss://relay.tunnellio.site/connect` с заголовками:

| Заголовок | Обязателен | Смысл |
| --- | --- | --- |
| `Authorization: Bearer <api-key>` | нет | без него выдаётся случайный поддомен |
| `X-Tunnellio-Version` | да | версия клиента, например `0.7.0` |
| `X-Tunnellio-Protocol` | да | версия протокола, начинаем с `1` |
| `X-Tunnellio-Domain` | нет | запрос конкретного поддомена, только с ключом |
| `X-Tunnellio-Resume` | нет | токен переподключения, см. §7 |

Ответ relay это первый управляющий кадр, JSON:

```json
{
  "ok": true,
  "protocol": 1,
  "domain": "tmp-3515952a.tunnellio.site",
  "url": "https://tmp-3515952a.tunnellio.site",
  "plan": "free",
  "resumeToken": "rt_...",
  "limits": {
    "maxStreams": 64,
    "maxBodyBytes": 33554432,
    "idleTimeoutSeconds": 300,
    "monthlyBytes": 10737418240
  },
  "notice": "Free tunnels get a new address on every start."
}
```

При отказе:

```json
{"ok": false, "code": "plan_required", "message": "Reserved domains need a paid key."}
```

**Закрытый список кодов:** `bad_key`, `plan_required`, `domain_taken`, `quota_exceeded`, `protocol_unsupported`, `rate_limited`, `server_error`.

Клиент обязан различать «отказ навсегда» (`bad_key`, `plan_required`, `protocol_unsupported`) и «попробовать позже» (`rate_limited`, `server_error`). В первом случае повторы запрещены: со стороны они выглядят как перебор.

## 5. Проксирование запроса

На каждый входящий HTTP-запрос relay открывает поток и пишет в него JSON-заголовок, завершённый переводом строки, затем тело как есть.

```json
{
  "id": "req_01H...",
  "method": "POST",
  "path": "/mcp",
  "query": "",
  "headers": {"content-type": "application/json"},
  "remoteAddr": "203.0.113.7",
  "contentLength": 812
}
```

Клиент отвечает симметрично: JSON-заголовок, перевод строки, тело.

```json
{"status": 200, "headers": {"content-type": "application/json"}}
```

Правила, которые легко забыть и потом ловить сутками:

* **`Host` подменяется** на `127.0.0.1:<port>`, исходный уходит в `X-Forwarded-Host`.
* **Добавляются** `X-Forwarded-For` и `X-Forwarded-Proto: https`.
* **Hop-by-hop заголовки вырезаются:** `Connection`, `Keep-Alive`, `Transfer-Encoding`, `Upgrade`, `Proxy-*`.
* **`Content-Length` пересчитывает та сторона, которая отдаёт тело.**
* **Сжатие сквозное.** Relay не распаковывает и не пережимает: пришло gzip, ушло gzip, заголовок сохранён. Мы уже наступали на это в 2.4.6, когда слой транспорта терял `content-encoding` и клиент получал бинарь под видом JSON. Симптом выглядел как нестабильный туннель, искали двое суток.

## 6. Стриминг и SSE

MCP использует Server-Sent Events, так что это не опция.

* Тело **не буферизуется целиком** ни на одной стороне.
* Нет `Content-Length` значит чанки идут потоком до закрытия.
* Для SSE relay обязан **отключить буферизацию** и сбрасывать каждый чанк немедленно.
* Idle-таймаут не применяется, пока по потоку идут данные.
* WebSocket-апгрейд внутри туннеля в первой версии **не поддерживается**, ответ `501`. Для MCP достаточно SSE.

## 7. Разрывы и переподключение

* **Keep-alive:** yamux ping каждые 30 секунд, три пропущенных значит соединение мертво.
* **Backoff:** 1, 2, 4, 8, 16, 30 секунд, дальше 30 с джиттером ±20%. Без джиттера тысяча клиентов после падения relay ложится на него синхронной волной.
* **Удержание домена:** при обрыве relay держит поддомен ещё **120 секунд** и отдаёт `resumeToken`. Вернувшийся с ним клиент получает тот же адрес. Иначе бесплатный туннель менял бы адрес при каждом чихе сети, что неотличимо от поломки.
* Пока клиента нет, relay отвечает **502 со страницей «туннель переподключается»**, а не рвёт соединение молча.

## 8. Домены

| | Бесплатно | Платно |
| --- | --- | --- |
| Адрес | `tmp-<8hex>.tunnellio.site`, новый при каждом запуске | зарезервированный поддомен |
| Своё имя | нет | да |
| Удержание при обрыве | 120 с | 120 с |
| Интерстишл при первом заходе | да | нет |

Случайное имя обязано быть **непредсказуемым** (CSPRNG, не счётчик и не время): адрес это часть защиты, пока клиент не настроил свою авторизацию.

## 9. Совместимость

* `protocol` целое число. Relay держит текущую версию и одну предыдущую.
* Неизвестные поля в JSON **игнорируются, а не роняют разбор**. Единственный способ добавлять возможности без синхронного обновления всех клиентов.
* Клиент новее relay получает `protocol_unsupported` с человеческим текстом.

## 10. Критерий готовности

1. Эталонные примеры всех кадров лежат в `docs/plan/fixtures/`.
2. Есть набор тестов совместимости, гоняемый против обеих реализаций.
3. Проверены: обычный запрос, крупный gzip-ответ, SSE на 60 секунд, обрыв с переподключением, каждый код отказа.
