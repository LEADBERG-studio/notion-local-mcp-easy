# Tunnellio relay: что доделать на сервере

**Читать после** `00-protocol.md`. Здесь только серверная часть.

---

## 1. Из чего состоит

```
            интернет :443
                 |
            [ Caddy ]  wildcard *.tunnellio.site, TLS, HTTP/2
                 |  (localhost)
            [ relay ]  WSS /connect, реестр сеансов, маршрутизация по Host
              /      \
     [ PostgreSQL ]  [ метрики ]
```

Caddy берёт на себя сертификаты, TLS и редирект с 80. Relay занимается только туннелями и никогда не разговаривает с интернетом напрямую.

## 2. Первый блокер: wildcard-сертификат

Сертификат на `*.tunnellio.site` выдаётся **только по DNS-01**: нужно уметь создавать TXT-запись `_acme-challenge`. Значит нужен **API-токен DNS-провайдера** и соответствующий плагин Caddy.

Без этого никакого 443 не будет, поэтому это задача номер один.

```
{
  acme_dns <provider> {env.DNS_API_TOKEN}
}

*.tunnellio.site, tunnellio.site {
  reverse_proxy 127.0.0.1:8080 {
    flush_interval -1          # SSE не буферизуется, критично для MCP
    transport http {
      read_timeout 0           # долгие потоки не рвём
    }
  }
}
```

`flush_interval -1` не украшение: без него SSE копится в буфере и MCP выглядит зависшим.

Отдельная запись `relay.tunnellio.site` для эндпоинта `/connect`.

## 3. Ядро relay

### Реестр сеансов

| Что храним | Где | Зачем |
| --- | --- | --- |
| поддомен → сеанс | память | маршрутизация каждого запроса |
| `resumeToken` → поддомен | память, TTL 120 с | вернуть тот же адрес после обрыва |
| зарезервированный домен → ключ | PostgreSQL | домен не должен уехать чужому |
| счётчики трафика | память, сброс в БД раз в минуту | квоты |

Поиск по поддомену на **каждый** входящий запрос, поэтому только хеш-таблица в памяти, никаких походов в базу.

### Маршрутизация

1. Из `Host` вырезаем поддомен.
2. Нет сеанса и нет удержания → **404** со страницей «туннель не найден».
3. Есть удержание, но клиент отвалился → **502** «переподключается», `Retry-After: 5`.
4. Есть сеанс → открываем yamux-поток и проксируем по §5 протокола.

### Что легко сделать неправильно

* **Не читать тело в память целиком.** Загрузка файла на 200 МБ не должна становиться 200 МБ в куче relay. Только потоковое копирование с ограниченным буфером.
* **Ограничить число потоков на сеанс** (`maxStreams`). Иначе один клиент под нагрузкой заполнит собой весь relay.
* **Таймаут на всё.** Поток без данных дольше `idleTimeoutSeconds` закрывается. Забытый таймаут это утечка, которая проявится через неделю аптайма.
* **Сжатие не трогаем.** Ни распаковки, ни пережатия, `content-encoding` сохраняется как есть.

## 4. Ключи и квоты

Что нужно в PostgreSQL:

```sql
create table api_keys (
  id            bigserial primary key,
  key_hash      bytea not null unique,   -- хеш, не сам ключ
  owner_id      bigint not null,
  plan          text not null default 'free',
  status        text not null default 'active',
  created_at    timestamptz not null default now(),
  last_seen_at  timestamptz
);

create table reserved_domains (
  subdomain   text primary key,
  key_id      bigint not null references api_keys(id),
  created_at  timestamptz not null default now()
);

create table usage_counters (
  key_id      bigint not null references api_keys(id),
  period      date not null,
  bytes_in    bigint not null default 0,
  bytes_out   bigint not null default 0,
  sessions    integer not null default 0,
  primary key (key_id, period)
);
```

**Ключи хранятся хешем.** Утечка дампа не должна давать рабочие ключи.

Проверка ключа при каждом `/connect` уходит в базу, но это раз в сеанс, а не раз в запрос. Кешировать результат на 60 секунд, отзыв ключа применяется не мгновенно и это нормально.

Эндпоинт валидации ключа **уже существует** (используется в контуре `tunnellio_random`), его надо переиспользовать, а не писать заново.

## 5. Что гейтим деньгами

Защита в тариф **не входит.** Продукт даёт модели файловую систему и запуск команд: незащищённый публичный туннель к такому это не «функция без защиты», это чужой сервер, который вскроют, и напишут об этом в блоге с нашим названием в заголовке. Один такой пост дороже всей выручки с тарифов.

Гейтим то, что стоит нам денег и приносит деньги клиенту:

| | Бесплатно | Платно |
| --- | --- | --- |
| Адрес | случайный, новый каждый запуск | зарезервированный, свой |
| Одновременных туннелей | 1 | по тарифу |
| Трафик | лимит в месяц | больше |
| Длительность сеанса | ограничена | без ограничения |
| Интерстишл при первом заходе | да | нет |
| Контроль доступа (позже) | нет | да |

Бесплатный тариф намеренно неудобен для прода и безупречен для «попробовать». Это ровно модель ngrok, и она работает. Интерстишл при этом бесплатный маркетинг.

Фраза для клиента звучит не «платите за защиту», а «платите за постоянный адрес и нормальные лимиты».

## 6. Второй блокер: ёмкость

Тысячи одновременных соединений это:

* **Файловые дескрипторы.** Минимум 2 на сеанс. `ulimit -n` поднять до 65535, в systemd-юните `LimitNOFILE=65535`. Дефолтная 1024 упрётся на пятистах клиентах.
* **Память.** Считать честно: yamux-сеанс плюс буферы это порядка 64–128 КБ на клиента при малой нагрузке. Тысяча клиентов это 64–128 МБ только на буферы, плюс всплески на активных потоках. Нужно решить, сколько памяти отдаём, и выставить жёсткий предел на число сеансов, который relay соблюдает сам, а не падает по OOM.
* **Сетевые настройки:** `net.core.somaxconn`, `net.ipv4.tcp_max_syn_backlog`, диапазон эфемерных портов.

**Нагрузочный тест обязателен до запуска:** 1000 висящих сеансов плюс 100 запросов в секунду через них, час подряд. Смотрим RSS, дескрипторы и p99. Не сделаем сейчас, узнаем от клиентов.

## 7. Наблюдаемость

Минимум, без которого потом невозможно разбираться:

* Метрики: активные сеансы, запросы в секунду, p50/p95/p99 задержки, ошибки по кодам, трафик, число переподключений.
* Структурные логи с `id` запроса из §5 протокола: он позволяет сшить событие на relay с событием у клиента.
* Health-эндпоинт для мониторинга.
* **В логи не попадают** ни ключи, ни тела запросов. Логи имеют свойство утекать.

## 8. Порядок работ

| # | Что | Готово, когда |
| --- | --- | --- |
| 1 | DNS-токен, Caddy, wildcard | `https://любое-имя.tunnellio.site` отвечает 404 от relay |
| 2 | Скелет relay: WSS, yamux, реестр | тестовый клиент проксирует GET |
| 3 | Проксирование по §5 полностью | проходят тесты совместимости из `fixtures/` |
| 4 | SSE и стриминг | поток на 60 секунд не рвётся и не буферизуется |
| 5 | Переподключение и удержание домена | обрыв на 30 секунд, адрес тот же |
| 6 | Ключи, домены, квоты | платный ключ получает свой домен, бесплатный случайный |
| 7 | Лимиты, метрики, нагрузочный тест | 1000 сеансов час без роста памяти |

Пункты 1–5 это минимум, с которым уже можно стыковать клиента и контур.
