Главное правило

Не публикуйте токены, owner code, client secret и локальные config-файлы.

IDE Gateway — мост между IDE и моделью

ide_gateway — это плагин, который поднимает локальный OpenAI-compatible endpoint на 127.0.0.1:8787. IDE видит его как обычного AI-провайдера, но за ним стоит активная MCP-модель с доступом к вашим файлам, shell и вебу. Мост работает через run_program: модель запускает bridge_step.py poll, обрабатывает запрос и отвечает через bridge_step.py complete.

Зачем это нужно: инструменты MCP менее надёжны, чем у IDE. Этот плагин позволяет работать в привычном IDE, но с моделью, которая видит ваши файлы и может вызывать MCP-инструменты. Общение IDE ↔ модель идёт напрямую, без сообщений в чате.

Как это работает

IDE (Cursor, Continue, VS Code, ...)
  → POST http://127.0.0.1:8787/v1/chat/completions
  → ide_gateway endpoint (worker)
  → очередь (file-based queue)
  → модель вызывает run_program: bridge_step.py poll
  → bridge_step.py забирает запрос из очереди
  → модель обрабатывает MCP-инструментами
  → модель вызывает run_program: bridge_step.py complete
  → IDE получает ответ
  → модель снова poll (цикл, без чат-сообщений)

Быстрый старт

  1. Запустите рабочую область в trusted developer mode.
    Через SETUP.bat в корне MCP включите trusted mode ответом y.
  2. Включите плагин.
    Откройте plugins\ide_gateway и запустите SETUP.bat. Выберите current scope, full_access mode, defaults.
  3. Перезапустите MCP.
    STOP.bat → START.bat. Endpoint поднимется на 127.0.0.1:8787.
  4. Получите промт-шаблон.
    Вызовите ide_gateway_bridge_prompt — он вернёт готовую инструкцию для системного промта Notion Agent.
  5. Вставьте промт в системный промт.
    Модель запустит цикл wait_request → мост стоит постоянно.
  6. Скопируйте настройки в IDE.
    Вызовите ide_gateway_show_config (include_secret=true) и скопируйте base_url, api_key, model.
  7. Работайте.
    IDE отправляет запросы — модель обслуживает их напрямую через мост.

Поддерживаемые эндпоинты

  • /v1/chat/completions (stream + non-stream)
  • /v1/responses (stream + non-stream, background, cancel, input_items)
  • /v1/completions (legacy)
  • /v1/models
  • /v1/tools + forced tool_choice
  • /v1/files (upload, list, get, content, delete)
  • /v1/images/generations, /v1/images/edits
  • /v1/audio/speech, /v1/audio/transcriptions, /v1/audio/translations
  • /v1/embeddings (local fallback)
  • /v1/moderations (local heuristic)

Цикл моста

  1. Модель один раз запускает цикл (через промт-шаблон или вручную).
  2. Модель вызывает run_program: python bridge_step.py poll --timeout 30 — это блокируется до прихода IDE-запроса (или 30 сек таймаут).
  3. IDE отправляет POST /v1/chat/completions → worker кладёт запрос в очередь → poll мгновенно возвращает его модели.
  4. Модель обрабатывает запрос своими MCP-инструментами (read_file, run_command, web_search и т.д.).
  5. Модель вызывает run_program: python bridge_step.py complete --request-id req_XXX --content "ответ".
  6. IDE получает ответ. Модель снова вызывает poll. Цикл повторяется без сообщений в чате.
Важно: мост держится только пока активная модель в чате запускает bridge_step.py poll в цикле. Если чат закрыт или модель не запустила цикл — запросы из IDE будут висеть в очереди до таймаута. Не вызывайте wait_request как MCP-tool-call — он таймаутит; используйте run_program + bridge_step.py.

Диагностика

  • ide_gateway_status — статус endpoint + счётчики очереди (pending/claimed/completed/failed/expired).
  • ide_gateway_show_config — готовые настройки для IDE.
  • ide_gateway_get_logs — последние записи (секреты замаскированы).
  • Endpoint state и очереди живут в gitignored temp/ide_gateway_runtime/.
