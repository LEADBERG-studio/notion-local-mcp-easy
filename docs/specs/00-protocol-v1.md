# Tunnellio Tunnel Protocol v1 (TTP/1)

**Статус:** проект, обязателен к согласованию до начала работ
**Владелец документа:** этот файл — единственный источник истины для relay и клиента
**Версия протокола:** `ttp/1`

---

## Зачем этот документ существует отдельно

Relay и клиент разрабатываются как две независимые программы, возможно в разных
сессиях и разными исполнителями. Если каждая из них будет описывать протокол
своими словами, они разойдутся, и отладка превратится в археологию.

Поэтому порядок работ такой:

1. **Этот документ фиксируется.** Он контракт.
2. Relay и клиент пишутся **параллельно**, каждый против контракта.
3. Контур в MCP-сервере пишется третьим, потому что он зависит от готового CLI
   клиента (он его просто запускает), но не от внутренностей relay.

Любое изменение протокола после начала работ — это правка **здесь** и
синхронное обновление обеих сторон.

---

## 1. Модель

```
[MCP-сервер :8765]  <--HTTP-->  [agent = tunnellio CLI]
                                        |
                                        | одно исходящее WSS-соединение на 443
                                        v
                                [Caddy :443 (TLS)]
                                        |
                                  loopback HTTP
                                        v
                                    [relay]
                                        ^
                                        | входящие запросы от клиентов
                                        |
                              https://<domain>.tunnellio.site
```

**Главный принцип:** агент устанавливает **исходящее** TLS-соединение на порт 443
и держит его. Никаких слушающих портов на машине пользователя, никакого
`ssh -R` в списке процессов. Именно это снимает поведенческие детекты
антивирусов (правило класса *Potential SSH Reverse Port Forwarding*,
MITRE T1572): для системы это неотличимо от браузера.

## 2. Установление соединения

### 2.1 Апгрейд

```
GET /v1/connect HTTP/1.1
Host: relay.tunnellio.site
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: <base64>
Sec-WebSocket-Protocol: ttp.1
```

Дополнительные заголовки агента:

| Заголовок | Обяз. | Значение |
| --- | --- | --- |
| `Authorization` | нет | `Bearer <api_key>`. Отсутствует → бесплатный тариф. |
| `X-Ttp-Client` | да | `tunnellio/1.2.0 (windows/amd64)` |
| `X-Ttp-Domain` | нет | Желаемый поддомен, например `mcp`. Только с ключом. |
| `X-Ttp-Resume` | нет | Токен возобновления из прошлой сессии. |
| `X-Ttp-Caps` | нет | Список возможностей через запятую, напр. `sse,ws,gzip-passthrough`. |

`Sec-WebSocket-Protocol: ttp.1` обязателен. Relay обязан вернуть его же.
Это дешёвая проверка версии до того, как стороны начнут говорить бинарно.

### 2.2 Отказ

Отказ — это **обычный HTTP-ответ до апгрейда**, с телом JSON. Никогда не
закрывать соединение молча: агент должен уметь показать оператору причину.

```json
{ "error": "domain_taken", "message": "mcp is reserved by another account", "retryAfter": null }
```

| HTTP | `error` | Смысл | Поведение агента |
| --- | --- | --- | --- |
| 400 | `bad_request` | Кривые заголовки | Выход, код 2 |
| 401 | `invalid_key` | Ключ не принят | Выход, код 3 |
| 402 | `plan_required` | Функция вне тарифа | Выход, код 4 |
| 403 | `domain_forbidden` | Домен не принадлежит ключу | Выход, код 5 |
| 409 | `domain_taken` | Домен занят живой сессией | Выход, код 5 |
| 426 | `version_unsupported` | Нет общей версии протокола | Выход, код 2 |
| 429 | `quota_exceeded` | Лимит сессий/трафика, есть `retryAfter` | Ретрай по `retryAfter` |
| 503 | `relay_draining` | Штатная остановка узла | Ретрай с backoff |

**Правило:** 4xx кроме 429 — это ошибка оператора или тарифа, ретраить
бессмысленно и вредно (пользователь не увидит причину за спамом попыток).
Ретраятся только 429, 5xx и сетевые сбои.

### 2.3 Первое сообщение

Сразу после апгрейда relay отправляет **текстовый** WS-фрейм с JSON `hello`.
До этого момента бинарных фреймов быть не должно.

```json
{
  "type": "hello",
  "protocol": "ttp/1",
  "sessionId": "s_7Kq2",
  "resumeToken": "rt_...",
  "domain": "mcp",
  "publicUrl": "https://mcp.tunnellio.site",
  "domainKind": "reserved",
  "plan": "pro",
  "limits": {
    "maxStreams": 256,
    "maxRequestBytes": 33554432,
    "idleTimeoutSeconds": 900,
    "resumeGraceSeconds": 90
  },
  "keepaliveSeconds": 30,
  "caps": ["sse", "ws", "gzip-passthrough"]
}
```

`domainKind`: `random` | `reserved`. Агент обязан вывести `publicUrl` **как
его вернул relay** и никогда не собирать URL самостоятельно из шаблона.

После `hello` соединение переходит в бинарный режим: все последующие
бинарные фреймы — это поток мультиплексора.

## 3. Мультиплексирование

**Библиотека:** `github.com/hashicorp/yamux`. Не изобретать фрейминг.

**Роли жёстко зафиксированы:**

* **relay = yamux client** (`yamux.Client`) — он **открывает** потоки, потому что
  инициатор всегда снаружи: пришёл HTTP-запрос → открылся поток.
* **agent = yamux server** (`yamux.Server`) — он только **принимает** потоки.

Единственное исключение — управляющий поток (§5), который открывает агент
сразу после `hello`.

Настройки yamux (обе стороны обязаны совпадать по духу):

```go
cfg := yamux.DefaultConfig()
cfg.EnableKeepAlive       = true
cfg.KeepAliveInterval     = 30 * time.Second
cfg.ConnectionWriteTimeout = 30 * time.Second
cfg.MaxStreamWindowSize   = 1 << 20   // 1 MiB, не 256 KiB по умолчанию
cfg.StreamOpenTimeout     = 15 * time.Second
cfg.StreamCloseTimeout    = 5 * time.Minute
```

Окно в 1 MiB — не косметика. При 256 KiB большой ответ упирается в
flow-control и начинает пилообразно тормозить на длинном RTT.

WS-фрейминг: yamux-поток пишется в WS **бинарными** фреймами. Использовать
`websocket.NetConn` (адаптер `net.Conn` поверх WS) — тогда yamux работает
последовательно и не требует своей нарезки.

## 4. Поток данных

Один yamux-поток = **одна HTTP-транзакция**. Никакого keep-alive внутри потока,
никакого пайплайнинга.

### 4.1 Что relay пишет в поток

Сырой HTTP/1.1 запрос, байт в байт, как он пришёл, с тремя правками:

1. `Connection: close` удаляется, hop-by-hop заголовки вырезаются
   (`Keep-Alive`, `Proxy-*`, `TE`, `Trailer`, `Upgrade` — кроме случая WS, §4.4).
2. Добавляются `X-Forwarded-For`, `X-Forwarded-Proto: https`,
   `X-Forwarded-Host: <domain>.tunnellio.site`.
3. Заголовок `Host` **сохраняется исходным**.

Всё остальное — не трогать. В частности:

> **Никакой перекодировки тела и никакого пересжатия.** Relay не разжимает и не
> сжимает ничего. Если апстрим прислал `Content-Encoding: gzip`, эти байты и
> этот заголовок должны доехать до клиента вместе. Мы уже теряли на этом сутки:
> прокси, который пересобирает ответ и роняет `content-encoding`, отдаёт клиенту
> бинарь под видом JSON, и это выглядит как «нестабильный туннель», а не как
> ошибка прокси.

### 4.2 Что агент пишет обратно

Сырой HTTP/1.1 ответ локального сервера, байт в байт. Агент — это `io.Copy` в
обе стороны, а не HTTP-клиент. Он не парсит ответ, не буферизует его и не
знает про его семантику.

Это главное архитектурное решение всего протокола. Оно бесплатно даёт
правильную работу chunked, SSE, trailers и апгрейдов.

### 4.3 Стриминг — жёсткое требование

MCP Streamable HTTP держит POST открытым и шлёт события по мере готовности.
Любая буферизация ломает продукт целиком.

**Обязательно:**

* relay не буферизует тело ответа: `http.Flusher.Flush()` после каждой записи,
  либо `io.Copy` в `http.ResponseWriter` без промежуточного `bufio` с большим
  буфером;
* `ResponseWriter` не должен иметь write deadline на время жизни потока;
* idle-таймаут потока считается от **последнего байта в любую сторону**, а не от
  начала запроса, и по умолчанию 900 секунд;
* если у Caddy впереди — `flush_interval -1` в `reverse_proxy` (иначе он
  буферизует SSE, это его дефолт для не-SSE ответов).

**Тест приёмки:** запрос, который отдаёт по одному байту раз в 5 секунд в
течение 2 минут, должен приходить по одному байту раз в 5 секунд, а не пачкой в
конце.

### 4.4 WebSocket сквозь туннель

В v1 достаточно поддержать апгрейд: если в запросе `Upgrade: websocket`, relay
передаёт его как есть и после ответа `101` перестаёт разбирать HTTP, просто
перекладывая байты. Агент делает то же самое. Отдельного механизма не нужно —
это следствие §4.2.

### 4.5 Лимиты

| Параметр | Значение | Поведение при превышении |
| --- | --- | --- |
| Размер тела запроса | 32 MiB (free), 256 MiB (pro) | `413`, поток закрывается |
| Размер заголовков | 64 KiB | `431` |
| Одновременных потоков | `limits.maxStreams` | `503` + `Retry-After: 1` |
| Время без байтов | `idleTimeoutSeconds` | закрытие потока, `504` наружу |

Превышение лимита потока **никогда** не должно ронять всю сессию.

## 5. Управляющий поток

Сразу после `hello` **агент** открывает первый yamux-поток и объявляет его
управляющим, отправив первой строкой:

```
TTP-CONTROL/1\n
```

Далее по этому потоку идут JSON-строки (NDJSON), в обе стороны.

| `type` | Направление | Смысл |
| --- | --- | --- |
| `ping` / `pong` | обе | Прикладной keepalive поверх yamux |
| `stats` | agent → relay | Счётчики агента раз в 60 с |
| `quota` | relay → agent | Остаток трафика/сессий, для предупреждений |
| `notice` | relay → agent | Текст оператору (напр. «тариф заканчивается») |
| `drain` | relay → agent | Узел уходит на обслуживание, переподключись |
| `domain_changed` | relay → agent | Домен переназначен (только для `random`) |
| `bye` | обе | Штатное закрытие с причиной |

Почему отдельный поток, а не текстовые WS-фреймы: после начала бинарного
обмена смешивать текст и бинарь в одном WS-соединении — источник трудноуловимых
гонок в библиотеках. Один транспорт, одна дисциплина.

## 6. Переподключение и удержание домена

1. Агент теряет соединение → сразу пробует `X-Ttp-Resume: <resumeToken>`.
2. Relay в течение `resumeGraceSeconds` (по умолчанию 90) держит запись домена
   живой и **не отдаёт домен никому**. Входящие запросы в это окно получают
   `502` с телом `agent_reconnecting` и `Retry-After: 2`.
3. Успешный resume → тот же домен, новый `sessionId`, новый `resumeToken`.
4. Истекла grace → сессия удаляется. Для `reserved` домен остаётся за ключом.
   Для `random` домен освобождается и при следующем подключении будет **другим**.

**Backoff агента:** 0.5с, 1, 2, 4, 8, 15, 30, далее 30 с полным jitter
(`sleep = random(0, cap)`). Без jitter массовый разрыв на relay превращается в
синхронный шторм переподключений.

**Никакого молчаливого переключения.** Если домен сменился, агент обязан
напечатать событие `url_changed`, а под флагом `--strict-domain` — завершиться
с ненулевым кодом. Это прямое следствие правила продукта: контур никогда не
подменяет себя другим за спиной оператора.

---

## 7. Матрица учётных данных

| Ключ | Домен | Тариф | Поведение |
| --- | --- | --- | --- |
| нет | случайный | free | Работает сразу, домен меняется при каждом запуске |
| есть | не задан | по ключу | Случайный домен, но с квотами тарифа |
| есть | задан, свободен | pro | Резервируется за ключом |
| есть | задан, чужой | — | `409 domain_taken`, отказ |

**Защита есть всегда и у всех.** Она не входит в тариф. Тариф — это постоянный
адрес, квоты и контроль доступа. Бесплатный туннель без защиты к продукту,
который даёт модели файловую систему и запуск команд, — это не «функция», это
инцидент, ожидающий своего блогера.

---

## 8. Совместимость и версионирование

* Ломающие изменения → `ttp/2`, новый `Sec-WebSocket-Protocol`.
* Relay обязан поддерживать `ttp/1` минимум 12 месяцев после выхода `ttp/2`.
* Новые возможности объявляются через `X-Ttp-Caps` / `hello.caps` и обязаны
  деградировать: агент без capability работает, просто без неё.
* Неизвестные поля JSON игнорируются, не являются ошибкой.
